\## 🔄 Lumière 前端網頁優化與跨平台無縫對接流程

這個流程分為三個核心衝刺（Sprints），核心目標是：\*\*「前端換膚、架構對齊、代碼防禦」\*\*。

```text
\[現有 React 程式碼] ──> (Sprint 1: 樣式 Token 化) ──> (Sprint 2: 元件防禦與異常防範) ──> (Sprint 3: 數據與 JSON 對齊) ──> \[升級版 Web + 準備就緒的 Flutter 規格]
```

\### 🏃‍♂️ Sprint 1：視覺換膚與 Design Tokens 落地（立刻看到產出）

這個階段的目標是\*\*抽換現有的 CSS 變數\*\*，將外包定案的色調引入，並建立「全膚色包容性安全防線」。

1\. \*\*CSS 變數全域替換（全端工程師與組員 A 對接）\*\*：

\* 不要去翻動現有的 React 元件邏輯。直接修改 `index.css` 或全域樣式檔案，將既有的 CSS 變數（如工程師提到的 `#1a1a2e`, `#c68b6e`），一對一覆蓋替換為我們定案的 Token：

\* `--primary-color: #8C6239;` (暖栗棕)

\* `--background-color: #F5EBE0;` (杏仁奶白)

\* `--secondary-color: #1A365D;` (深海藍)

\* `--cta-color: #D4A373;` (琥珀金)

2\. \*\*落實膚色 Swatch 保護圈（UI 優化）\*\*：

\* 檢查現有網頁的結果頁（Result Page）。找到顯示 `skin\_hex` 與 `shade\_hex` 的 `<div>` 區塊。

\* 依據設計規範，為這些膚色色塊的父容器加上 `background-color: #FFFFFF;`，並補上 `border: 1px solid var(--primary-color);` 與軟陰影（`box-shadow`）。這能讓網頁在展示不同膚色時，\*\*立刻呈現出高質感的視覺包圍感\*\*，同時確保極淺膚色在杏仁奶白背景下不會溢出。




\---

\### 🏃‍♂️ Sprint 2：佈局防禦與滾動合規改造（為 Flutter 埋線）

這個階段解決\*\*多語系長文字擠壓破版\*\*的問題，並將 GDPR 彈窗改造成高合規版本。

1\. \*\*長文字換行與彈性高度優化（組員 A）\*\*：

\* 全面檢查 React 前端的 `button`、`card`、`checkbox` 等元件。

\* 移除所有程式碼中寫死的固定高度（例如 `height: 48px`），一律改用 `padding: 12px 16px` 或 `min-height` 撐開。

\* \*Flutter 對接點\*：這對應了 Flutter 中 `IntrinsicHeight` 的思維。現在把網頁的固定高度拔除，未來在 Flutter 寫 UI 時就不需要重新評估版面寬度。

2\. \*\*GDPR 全視窗滾動彈窗改造（組長 \& 組員 B）\*\*：

\* 現有的網頁只有簡單的 checkbox 同意文案。我們利用現有的 React Component 庫（或 Ant Design / Tailwind Modal），把乾淨 JSON 裡的 `gdprConsent` 長文本放入一個 `overflow-y: scroll` 的容器中。

\* 寫一段簡單的 JS 邏輯監聽滾動事件（`onScroll`），當使用者滾動到底部時，將原本 `disabled` 的 \*\*Amber Gold CTA 按鈕\*\*轉為 `enabled`。

\* \*實質產出\*：網頁產品的法律合規性瞬間達到 Production 級別，未來 Flutter 只需要照抄這個滾動解鎖的 Logic 即可。

\---

\### 🏃‍♂️ Sprint 3：資料結構與語系資源標準化（後端與 i18n 串接）

這個階段是前後端架構的收尾，確保網頁版與未來的 Flutter App 讀取的是同一套邏輯。

1\. \*\*全面替換為 `translations.clean.json`（組員 A）\*\*：

\* 把全端工程師提供的乾淨 6 語系 JSON 檔案，正式部署到網頁端的 i18n 配置中（取代原本有亂碼的 `translations.js`）。

\* 網頁端切換語系時，檢查法文、土耳其文和葡萄牙文是否有因為字串過長而導致字體重疊，並利用 CSS 的 `word-break: break-word` 進行修復。

2\. \*\*異常狀態（Error States）與結構化錯誤碼對接（全端工程師 \& 組員 B）\*\*：

\* 目前網頁端遇到 422 錯誤一律簡化顯示「無法偵測到臉」。

\* \*\*修改流程\*\*：請全端工程師配合，讓 FastAPI 在回傳錯誤時帶上結構化的 `error\_code`（例如 `IMAGE\_TOO\_DARK`, `IMAGE\_TOO\_BRIGHT`）。

\* 網頁前端收到 `error\_code` 後，利用 `switch-case` 條件渲染，依據不同的錯誤碼，動態展示我們選定的 \*\*Lucide Icons\*\* 與對應語系的錯誤文案（如：`errors.tooDark`）。

\* \*Flutter 對接點\*：這是一招完美的「隔山打牛」。當網頁端把這套結構化錯誤碼串好後，未來的 Flutter App 只需要寫一套一模一樣的 `switch(errorCode)`，就能直接調用 App 端的插畫元件，前後端邏輯完全同步。
